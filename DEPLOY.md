# Deploying to Render

The app deploys as **one service**. `backend/main.py` serves the built React
bundle itself, so there is no separate frontend host, no CORS in production, and
no cross-origin cookie problem. The Dockerfile builds the frontend in a Node
stage and copies `dist/` into the Python image.

Total moving parts: **one web service + one Postgres + one 1 GB disk.**

`render.yaml` in the repo root declares all three, so most of this is one click.

---

## 1. Push to GitHub

```bash
git remote add origin git@github.com:<you>/dfs-console.git
git branch -M main
git push -u origin main
```

The repo is already initialized with a first commit. **Make it private** — it
carries slate fixtures, and secrets live in the dashboard, never in git.
`.env` and `blobs/` are gitignored; keep it that way.

## 2. Apply the Blueprint

Render dashboard → **New** → **Blueprint** → select the repo → **Apply**.

Render reads `render.yaml` and provisions the web service, the Postgres, and
the disk in one pass, wiring `DFS_DATABASE_URL` to the database's connection
string automatically. First build takes ~5 min: npm install plus a from-source
`ortools` wheel.

If you have the CLI, `render blueprints validate` catches YAML errors before
you burn a build.

## 3. Fill in the four secrets

The Blueprint marks these `sync: false`, which means Render deliberately leaves
them blank for you. Service → **Environment**:

| Variable | Value |
|---|---|
| `DFS_ODDS_API_KEY` | your **rotated** key — not the one that was in `config.py` |
| `DFS_FANTASYPROS_API_KEY` | your key |
| `DFS_BOOTSTRAP_USER` | `cade` |
| `DFS_BOOTSTRAP_PASSWORD` | a strong password, used once |

`DFS_SESSION_SECRET` is generated by Render (`generateValue: true`) — leave it
alone. Everything else is already set in `render.yaml`.

Save; Render redeploys.

## 4. Log in, then delete the bootstrap credentials

1. Open the `onrender.com` URL from the service page.
2. Log in with the bootstrap username and password.
3. **Delete `DFS_BOOTSTRAP_USER` and `DFS_BOOTSTRAP_PASSWORD`** and redeploy.

They exist only so a fresh database can mint its first account without shell
access. The startup hook is idempotent and skips an existing username, but
leaving a plaintext password in the environment is pointless risk once you can
log in.

Add the other two accounts from the dashboard shell:
`python -m backend.auth.seed <username>`.

Migrations need no attention: the container's start command is
`alembic upgrade head && uvicorn ...`, and a disk-attached service runs a
single instance, so there is no concurrent-migration race.

## 5. Verify before trusting it with a slate

- `https://<your-app>.onrender.com/api/health` → `{"ok": true}`
- Slates → **Ingest fixture slate** → Simulate → build 5 lineups.
  This exercises ingest → simulate → solve → export against committed fixtures
  and spends **zero** API credits. Do this before the live pull.
- Redeploy, then reload a lineup set. If the sims survived, the disk is mounted
  correctly. If the app re-simulates, `DFS_BLOB_DIR` is not on `/data`.

## Things specific to Render worth knowing

**Use Standard, not Starter.** Starter is 512 MB / 0.5 vCPU. The sims matrix is
~110 MB resident as float32 before numpy's working copies, and CP-SAT candidate
generation wants a full core. Standard (2 GB / 1 vCPU) is the floor for this
workload on any host.

**The free Postgres tier expires after 90 days.** `render.yaml` specifies
`basic-256mb` for that reason. Confirm the current plan name and price before
applying — Render restructured pricing in April 2026 and the names move.

**Egress is metered now.** The April 2026 repricing cut included bandwidth to
5 GB on Hobby and 25 GB on Pro, $0.15/GB over. Three users and CSV exports will
not come close, but it is the trap in the current pricing if the app ever grows
a public surface.

**You pay for idle.** Render bills a fixed instance price whether or not the
service is doing anything, and this app is idle six days a week. That is the
deliberate trade: predictable billing and a better reliability record, against
metered platforms that are cheaper for bursty work. Roughly $30–40/mo all-in
against the ~$40/mo you already spend on FantasyPros and the Odds API.

**`region` and `databaseName` cannot be changed after creation.** The Blueprint
sets `ohio` for both, the closest region to Central. Change it before the first
apply if you want otherwise, not after.

**Do not add a second instance.** A service with an attached persistent disk
can't scale horizontally — Render will reject it. That constraint is fine here
and is part of why the single-service shape works.

## Sizing floor, whichever host

- **≥ 2 GB RAM** — sims matrix resident in the API process (requirements §12)
- **≥ 1 vCPU** — CP-SAT candidate generation is the bottleneck
- **Persistent disk or object storage** — sims blobs must survive redeploys

## When to add the worker (not yet)

`DFS_JOB_MODE=thread` runs builds inside the API process. For three users and a
build every few days that is correct — CP-SAT releases the GIL, so request
handling stays responsive. Add a background worker only when a 150-lineup build
makes the UI sluggish:

1. New `type: worker` service in `render.yaml`, same repo, start command
   `python -m backend.worker`.
2. Add a `type: keyvalue` service; set `DFS_REDIS_URL` on **both** services and
   `DFS_JOB_MODE=rq` on the web service.
3. **A Render disk mounts to exactly one service.** Once a worker writes sims
   the web service reads, move blobs to object storage: implement the
   `BlobStore` protocol in `backend/storage/` against Cloudflare R2 (S3 API, no
   egress fees), as §11d specifies. `LocalBlobStore` is ~40 lines; the R2
   version is about the same.

Do not skip ahead to this. The single service is the correct starting shape.

## Scheduled pulls

`backend/scheduler.py` holds `PULL_SCHEDULE` — ten weekly pulls in
America/Chicago, of which the Sunday 10:30am inactives pull is the highest-value
one of the week. Render cron jobs are `type: cron` services in `render.yaml`
with a `schedule` expression; they run the container, exit, and bill for the
seconds used. **Cron schedules are UTC**, so the Central times have to be
converted and will drift an hour at DST — which is exactly the failure §15b
warns about. Wire these up only with an alert on failure attached; a silently
missed inactives pull produces a bad slate rather than an error.

Manual ingest from the UI is fine until then.

## Docker Compose (local, optional)

`docker-compose.yml` still runs Postgres + Redis + api + rq worker locally if
you want to exercise the RQ path before deploying it. Nothing in the Render
deploy depends on it.

## If you ever move off Render

The Dockerfile is the whole deployment contract, so this is not lock-in.

- **Railway** — `railway.json` is still in the repo and works: usage-metered
  billing suits a workload that idles most of the week, and the DX is the best
  of the three. Its 2026 reliability record is the reason it is not the primary
  path here: five major platform incidents between November 2025 and May 2026,
  including an eight-hour control-plane outage. Your hard requirement is a
  four-hour window on Sunday morning; that is the wrong risk to take for a few
  dollars a month.
- **Fly.io** — cheapest raw compute, and `auto_stop_machines` fits an app that
  idles six days a week. Costs a `fly.toml`, flyctl, and running your own
  Postgres.
- **Hetzner + Coolify/Dokploy** — far more CPU per dollar, which starts to
  matter if sim counts grow. You own patching, backups, and uptime.
- **Your own Ubuntu box + Tailscale** — zero hosting cost, 32 GB of RAM, and it
  already holds the DuckDB historical store that requirements items 12–14 need.
  Auth is already built, so Tailscale only has to handle reachability for three
  known users. The trade is that a Sunday power or ISP failure is unfixable
  remotely.
